# 레거시 모듈 문서화

대상: $ARGUMENTS (첫 인자 = 모듈 경로, 둘째 인자 = 범위 제한. 범위가 있으면 그 밖은 "범위 밖"으로만 적는다)

## 원칙
- 분석 대상 폴더의 파일은 읽기만 한다. 수정 · 포맷팅 · 실행 결과 저장을 하지 않는다.
- 산출물 폴더 `docs/<모듈명>/` 의 `<모듈명>` 은 폴더 이름이 아니라 다음 중 하나다.
  - `legacy/item-bank-php` → `item-bank`
  - `legacy/assignment-thymeleaf` → `assignment`
  - `legacy/grade-mssql` → `grade`
  - 셋 중 어디에도 해당하지 않으면 진행하지 않고 묻는다.
- 단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다. 저장하지 않고 다음 단계를 시작하지 않는다.
- 모든 주장에는 근거를 `파일:줄번호` 로 붙인다. 근거를 못 찾은 내용은 "미확인" 절로 보낸다.

## 절차
1. **계획 제시** — 파일 목록(`find`/`Glob`)과 줄 수만 보고 읽을 순서 · 단계별 산출물 · 범위를 제시한다. 사용자 확인 뒤 시작한다.
2. **진입점** — 요청을 받는 곳(PHP 페이지, `@Controller` 매핑, 저장 프로시저 호출부 등)을 표로 정리한다.
   URL/호출명 · 파일:줄번호 · 역할. → `ARCHITECTURE.md` 에 저장.
3. **의존 관계** — 진입점에서 include · 주입 · 호출되는 파일/클래스를 따라가 호출 방향(A → B)을 적는다.
   실제로 호출문이 있는 방향만 적는다. → `ARCHITECTURE.md` 에 추가 저장.
4. **데이터 흐름** — 스키마(`db/`)와 SQL 을 읽어 테이블 목록 · 관계 · 읽기/쓰기 위치(파일:줄번호, SELECT/INSERT/UPDATE/DELETE)를 정리한다.
   Mermaid `erDiagram` 1개를 넣는다. → `ERD.md` 에 저장.
5. **비즈니스 규칙 후보** — 조건문 · SQL WHERE · 검증 · 기본값 · 매직 넘버에서 규칙을 뽑는다. → `BUSINESS-RULES.md` 에 저장.
   절 구성: 먼저 볼 것(이관 시 결정 필요) · 영역별 규칙 · 같은 규칙의 다른 구현 · 매직 넘버 · 주석만 있는 것 · 미확인.
6. **표본 점검 추천** — 사람이 코드로 확인할 규칙 3개를 추천한다(아래 참고).

## 규칙 형식

| ID | 규칙 | 근거 | 근거 코드 | 확신도 | 비고 |
|---|---|---|---|---|---|
| BR-01 | 한 문장, 입력 → 결과로 쓴다 | `search.php:522` | `` `원문 그대로 인용` `` | 확실 | 주석 · 스키마와 다르면 여기 적는다 |

- ID 는 `BR-<두 자리>` 로 매기고 한번 붙인 번호는 바꾸지 않는다.
- 근거 코드는 파일에서 복사한 원문이다. 여러 줄이면 `<br>` 로 잇는다. 요약 · 재작성하지 않는다.
- 확신도: **확실**(조건문 · SQL 을 읽어 확인) / **추정**(코드에서 추론, 추론 근거를 비고에) / **미확인**(근거 부족).
- 코드를 실행하지 않았으면 문서 머리에 "실행해 보지 않았다"고 적는다.

## 하지 말 것 (item-bank 검증 이력에서 실제로 틀린 유형)
- **코드에 없는 동작을 DB 기본값으로 짐작하지 않는다.** 대소문자 무시(BR-09 · BR-10 · BR-19)를 콜레이션 짐작으로
  "같은 결과가 나온다"고 썼다가 모두 "정확 일치, 대개 0건"으로 뒤집혔다. 비교 함수 · 콜레이션 정의를 인용 못 하면 "미확인".
- **변환 후 결과가 "나온다"고 단정하지 않는다.** `03` · `3.5` → `3` 으로 결과가 나온다(BR-14)고 썼지만
  실제는 경고 후 `(int)` 값으로 비교해 대개 0건이었다. 변환 뒤 어느 분기 · 어떤 비교로 가는지까지 따라간다.
- **경계값 분기를 빠뜨리지 않는다.** page=0 을 "경고 없이 1페이지"(BR-31)로 썼지만 0 이하 · 비숫자는 경고가 붙었다.
  0 · 음수 · 비숫자 · 최댓값 초과를 조건문마다 각각 확인한다.
- **코드가 조회하는 대상과 스키마 정의를 섞지 않는다.** "`status='A'` 만 검색"(BR-01)은 뷰 정의에서 가져온 것이고
  코드는 `v_item_public` 만 조회했다. 규칙은 코드가 실제 쓰는 이름으로 적고, 뷰 · 트리거 내부는 따로 표시한다.
- **잠금 · 동시성은 대상과 방식을 특정한다.** "조회할 때 잠금"(BR-44)이 아니라 "`item` 을 `FOR UPDATE` 로 잠그고 MAX+1"처럼 쓴다.
- **인용한 코드와 규칙 문장이 서로 맞는지 저장 전에 대조한다.** 판정 때 "코드 인용과 다름"이 3건 나왔다.
- 존재하지 않는 함수 · 파일을 적지 않는다. 적기 전에 `grep` 으로 정의 위치를 확인한다.
- 주석 · 변수명만 보고 규칙을 만들지 않는다. 주석만 있는 것은 "주석만 있고 코드로 확인되지 않은 것" 절로 보낸다.

## 마지막 단계: 표본 점검 추천
`BUSINESS-RULES.md` 끝에 "사람이 표본 점검할 규칙 3개" 절을 두고 다음을 섞어 고른다.
1. **가장 그럴듯한 규칙** — 확신도 "확실"이고 상식에 잘 맞아 아무도 의심하지 않을 규칙 1개(틀리면 가장 늦게 발견된다).
2. 입력 변환 · 경계값 · 대소문자처럼 위 "하지 말 것" 유형에 해당하는 규칙 1개.
3. 이관 결정에 영향이 큰 "먼저 볼 것" 규칙 1개.

각각 ID · 확인할 파일:줄번호 · 확인 방법(어떤 입력으로 어느 분기를 따라가면 되는지)을 적는다.
점검 결과를 받으면 규칙을 고치고 "검증 이력" 절에 `날짜 — 규칙 ID: 이전 → 판정` 형식으로 남긴다.

## 완료 보고
만든 파일 3개의 경로, 규칙 수(확신도별), 미확인 항목 수, 표본 점검 추천 3개만 답변에 적는다.
