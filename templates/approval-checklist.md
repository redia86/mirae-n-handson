# 승인 체크리스트 v1

v1 · 2회차
- 테스트 기준: "충분한가"를 "새 public 메서드(접근자 제외)와 새 엔드포인트마다 테스트가 있는가"로 바꿨다.
- 치명 · 범위 기준: 치명을 네 가지(비밀값 노출 · 데이터 손실 · 인증 우회 · SQL 문자열 조립)로 한정하고, 범위 밖 변경은 같은 파일 안의 import 정리만 허용한다.
- 컨벤션 기준: 계층 규칙 위반 · 빈 catch · 임시 출력은 반려, 네이밍은 경고로 나누고 모든 항목을 예/아니오 문장으로 바꿨다.

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려.
항목은 모두 "예/아니오"로 답한다. 모두 "예"여야 그 기준이 충족이다.

## 심각도 정의

- **치명** — 아래 네 가지 중 하나. 1건이라도 있으면 반려.
  - 비밀값 노출
  - 데이터 손실
  - 인증 우회
  - SQL 문자열 조립
- **경고** — 치명은 아니지만 다음 변경에서 사고가 될 수 있는 문제. 네이밍 위반 같은 반려 대상이 아닌 컨벤션 위반도 여기에 둔다. 승인 여부는 리뷰어가 판단한다.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했는가?
- [ ] 실행 결과의 실패 · 오류가 0건인가?
- [ ] 새 public 메서드(getter · setter · 생성자 같은 접근자 제외)마다 테스트가 1개 이상 있는가?
- [ ] 새 엔드포인트마다 테스트가 1개 이상 있는가?
- [ ] 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없는가?

## 2. 치명 이슈 0건

- [ ] 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있지 않은가?
- [ ] 데이터를 지우거나 덮어쓰는 코드가 새로 생겼다면 요청에 그 내용이 명시돼 있는가?
- [ ] 인증 · 권한 검사를 우회하거나 제거한 곳이 없는가?
- [ ] SQL 을 문자열로 이어 붙여 만드는 곳이 없는가(파라미터 바인딩 사용)?

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었는가(없으면 판정하지 않고 먼저 묻는다)?
- [ ] 변경 파일 목록의 모든 파일이 요청 문장으로 설명되는가?
- [ ] 같은 파일 안의 import 정리를 제외하고, 요청과 무관한 변경(리팩터링 · 로그 포맷 · 이름 변경)이 없는가?
- [ ] 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면 요청에 포함돼 있었는가?

## 4. 컨벤션 준수

- [ ] 팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조했는가(`convention-check` Skill 이 있으면 그 결과를 쓴다)?
- [ ] 컨트롤러에서 Repository · SQL 을 직접 호출하는 곳이 없는가? (위반 시 반려)
- [ ] 예외를 잡고 아무 처리 없이 넘기는 빈 `catch` 가 없는가? (위반 시 반려)
- [ ] `System.out.println` · `printStackTrace()` · `console.log` 같은 임시 출력이 남아 있지 않은가? (위반 시 반려)
- [ ] 이름이 `CLAUDE.md` 의 네이밍 규칙(상수 `UPPER_SNAKE_CASE`, 이벤트 prop `on<동작>` 등)을 따르는가? (위반 시 경고)

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 코드는 수정하지 않는다.
